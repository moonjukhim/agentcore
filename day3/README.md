# 1

#### 다중 에이전트와 함께 쓰는 관련 패턴

| 패턴 | 해결하는 문제 | 다중 에이전트에서 쓰는 방식 |
|---|---|---|
| Tool Calling (21) | LLM이 외부 API를 호출해 실제 작업을 수행 | 전문가 에이전트를 도구로 노출하는 기반. MCP로 도구 정의를 표준화 |
| Grammar (2) | 출력 형식을 강제 | 라우터의 결정을 열거형 구조화 출력으로 제한하고 temperature를 0으로 둠 |
| Reflection (18) | 피드백을 반영해 이전 응답을 고침 | 작성자와 검토자 에이전트가 주고받는 루프. Graph 순환 엣지로 구현 |
| LLM-as-Judge (17) | 개방형 출력을 다차원으로 평가 | 검증 에이전트, 라우팅 품질 평가, 가드레일의 판정 엔진 |
| Dependency Injection (19) | 체인의 각 구성 요소를 독립적으로 개발·테스트 | 앞 단계 에이전트를 목(mock)으로 바꿔 끼우고 뒷 단계 에이전트만 테스트 |
| Long-Term Memory (28) | 상호작용을 넘어 정보를 유지 | 아래 메모리 4유형 표 참고 |
| Prompt Caching (25) | 반복 프롬프트의 비용·지연 | 전문가마다 고정된 시스템 프롬프트·도구 정의를 캐시 |
| Guardrails (32) | 보안, 개인정보, 콘텐츠 조정, 환각 | 입력·출력·검색·도구 호출을 감싼다. 10장은 가드레일을 **본 작업과 동시에 실행하고 실패하면 본 작업을 취소**해 지연을 없앰 |
| Degradation Testing (27) | 서비스 품질 저하 감지 | TTFT, 종단 간 지연, TPS, RPS를 에이전트별로 측정 |
| Self-Check (31) | 환각을 저비용으로 탐지 | 토큰 확률로 의심 구간을 표시. 사람이 검토를 건너뛰는 “자동화 피로” 대응에도 씀 |
